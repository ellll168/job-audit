01 · WHY

招聘 JD 是一份营销文本，不是事实描述

JD 由招聘方单方面撰写，写作目标是最小成本吸引尽可能多的投递，因此天然倾向于放大福利、隐藏缺陷。求职者手里只有这段文本，没有内部信息、没有历史评价，也没有可比对的基准。

一段真实风格的 JD（脱敏） "急招 Java 开发，薪资面议，能吃苦抗压，单休，领导交办的其他工作。"

这段 30 余字的话里同时藏着：薪资不透明（面议）、超时工作（抗压 + 单休）、职责无边界（领导交办的其他工作）、紧迫话术（急招）。任何一条都足以改变投递决策，但人在浏览时通常只会记住"急招 Java"。

现有工具的方向错位

工具类型回答的问题没有回答的问题
简历匹配 / 岗位推荐"我能不能拿到这个岗位"这个岗位值不值得去
薪资查询平台"这个岗位市场价多少"这家公司这段 JD 是否在压价
公司点评社区"别人在这家公司体验如何"这段具体文本里有哪些即时风险
本作品"这段 JD 本身暴露了什么"—（只做文本层风控，不做公司评价）

方向差异带来一个直接后果：求职者用面试成本、试用期成本去验证一个本可以在投递前识别的风险。本作品把这一步提前，且只依赖用户愿意提供的一段文本，不采集隐私、不依赖内部数据。

为什么这件事适合交给 AI，又不能全交给 AI

适合 AI 的部分
"公司是家""年轻人要能吃亏""发展空间巨大"这类话术没有固定词表，语义随上下文变化，正则无法穷举；需要模型理解言外之意。
不能交给 AI 的部分
"8K-30K"的跨度是 3.75 倍、"面议"就是没写数字、单休就是每周休一天——这些是确定事实，用模型判断反而引入不确定性。

01 · PRINCIPLES

三条设计原则，决定了后面的所有取舍

确定性优先
能用规则、数值比较、集合判断得出的结论，一律不进模型。模型只处理规则覆盖不到的语义区间，从源头降低不确定性。
结论可解释
每个信号都要能回到 JD 原文片段或明确规则；LLM 输出的 reason 必须引用原文关键短语，禁止空泛判断。
失败必须可见
AI 降级时明确提示"仅规则结果，语义风险可能漏检"，绝不输出"零信号 = 安全"的暗示。

结果页不是聊天框，而是结构化仪表盘

左栏：量化风险
顶部仪表盘给出 0–100 综合风险分（HIGH 30 / MEDIUM 15 / LOW 5，封顶 100）；雷达图把 11 类信号折叠成"职责模糊、薪资坑人、PUA 话术、信息缺失"四个维度，取该维度最高严重度。
右栏：逐条证据
每张信号卡展示类型、严重度、来源标签（RULE / LLM / SYSTEM）与 reason。HIGH 级卡片左侧用 CSS 伪元素画 45° 黄黑警戒线，颜色不是装饰而是等级编码。
顶部：一句话定性
毒舌锐评使用等宽字体、红色发光边框与倾斜的 [ WARNING: AI VERDICT ] 印章标签，让"判断"与"证据"在视觉上分层。
底部：可执行动作
避坑锦囊用琥珀色警示卡（红=警报、黄=行动、灰=信息）；面试反问按需生成，生成后回写数据库，重复查看不再调用模型。

两个容易被忽略的工程细节

结果可回看：页面把 auditId 写入 URL 查询参数，刷新或分享链接后自动按 ID 拉取历史记录，而不是重新调用模型。前端同时按需加载 html2canvas-pro 导出整页报告——原版 html2canvas 不支持 Tailwind v4 输出的 oklch() 颜色，会静默失败。

三者为什么没有互相串味

三块内容共享同一段 JD 与同一批风险信号，如果没有显式隔离，模型的默认行为是把它们写成同一类东西。实际观测到的三种越界是：锐评变成建议（"建议你面试问清底薪"）、锦囊变成提问清单（"去问 HR 薪资构成"）、反问变成第三人称分析（"该岗位薪资结构不透明"）。

解决办法不是加形容词，而是给每个字段定义唯一的言语行为与说话人：吐槽者只下判断、导师只讲该防什么、求职者只向 HR 发问。具体 Prompt 设计与代码闸门见第 13–19 页。

锐评：一句话
≤ 30 字，禁止建议、禁止问句、禁止并列多条。超长由代码硬截断。
锦囊：陈述句
2–3 条，每条 ≤ 30 字；解析层直接丢弃以问号结尾的行。
反问：疑问句
3 条，必须以"？"结尾；一行多问句按问号切分，混入的陈述句被剔除。

03 · ARCHITECTURE

分层架构：AI 只出现在一个可替换的格子里

整张图的画法本身就是一种约束：LLM 调用被收敛到 SignalExtractionService 与 AuditService 的三个生成方法中，不渗透到 Controller、规则引擎与持久化层。替换模型供应商，只需改一个 Bean。

图 1　系统分层。红色区域是唯一允许调用大模型的位置，其余模块对 AI 无感知。

这张图对应的四条硬边界

边界落地方式
Controller 不写业务只做参数校验、日志与响应组装，存库与模型调用全部委托给 Service。
规则与模型互不调用两者都只接收 JD 文本、返回信号列表；合并逻辑在编排层，规则不知道模型存在。
AI 不出现在事务里@Transactional 全项目只出现在 AuditPersistenceService 一处。
存储可替换MySQL 走 Flyway 迁移；演示与测试走 H2 兼容模式，DDL 结构保持一致。

为什么把 AI 收敛成一个格子

模型调用有三类不可控：延迟、输出格式、语义稳定性。把它们限制在一个 Service 里，等于把不可控因素关进一个可替换的边界——换模型只改一个 Bean，降级只改一个分支，测试只需 Mock 一个接口。反过来，如果模型调用散落在 Controller、规则引擎与持久化层，任何一次超时都会穿透整条请求链路，事务边界也无从谈起。

图中绿色区域与红色区域之间没有依赖：规则引擎不知道模型存在，模型也不读取规则的计算过程，两者只共享"JD 文本"这一个输入。

为什么把 AuditSignalRecordService 单独抽出来

第一版用 MyBatis-Plus 的静态工具 Db.saveBatch(...) 写库，代码更短，但静态调用无法被 Mockito 替换，导致"批量写入失败时主表是否回滚"这条最关键的断言根本写不出来。抽成一个 Bean 之后，测试可以用 @MockitoBean 让它抛异常，故障注入才成为可能。

这是一个典型的"为了可测试性牺牲一行代码的简洁"的取舍。类似的取舍还有：不让 AuditService 自己带事务注解，而是拆出持久化 Bean，避免 Spring 自调用绕过 AOP 代理。

为什么规则优先，而不是"模型更聪明就听模型的"

1. 可解释性不同。"8K-30K 的跨度是 3.75 倍"是一条可复算的事实；模型说"这个薪资不透明"是一个需要被信任的判断。当两者冲突时，前者更适合作为最终结论。

2. 失败方向不同。规则漏报是"少报一个已知模式"，可以通过补测试修复；模型误报是"在不该报的时候报了"，用户无法从结果里分辨。规则优先等于把最终裁决权留在确定性一侧。

3. 成本结构不同。规则先跑，可以在进入模型前就确定一部分结论；即使模型完全不可用，系统仍然能输出 7 类硬风险，而不是一片空白。

红线：不让模型做它不擅长的事

不做薪资数值计算
"上下限差 2 倍"由 BigDecimal 统一折算为元后比较，支持 8K-30K、8k~30k、8000-30000、1万-3万，以及混合单位 8K-3万。模型不参与数值判断。
不做严重度定级
模型只输出 0–1 的 confidence；severity 由服务端映射（≥0.8 HIGH / ≥0.5 MEDIUM / 其余 LOW）。避免模型同时决定"有多严重"和"有多确定"。
不做去重决策
合并逻辑在编排层完成，规则不知道模型存在，模型也不知道规则输出了什么。双方只面对 JD 文本。
不做安全兜底
模型不可用时，系统不猜测、不补全，而是明确标注"语义风险可能漏检"，把不确定性交还给用户。
设计意图（非实测）：这套划分的代价是规则覆盖范围有限，新话术需要人工补词表；收益是任何时候都有一条确定性的底线。对求职风控这类"宁可疑、不可漏"的场景，这个交换是值得的。

意图控制：四层约束，从"请模型配合"到"代码说了算"

04 · PROMPT STRUCTURE

System Prompt 的五段结构

语义提取的 System Prompt 固定为五段：角色、任务（含分类法）、Few-shot、约束、输出格式。段落顺序不是随意的——先建立身份，再划定范围，再用示例锚定粒度，最后用格式收口。

段落写了什么为什么必须有
# Role"资深求职风控专家，长期为求职者做招聘 JD 的反向尽调"给模型一个稳定的判断立场：站在求职者一侧，而不是中立描述
# Task只识别 4 类：pua_culture / overpackaged / broad_duty / salary_mismatch，每类给定义与典型表述封闭分类法，杜绝自创标签；每类都带口语化例子，降低抽象概念的理解方差
# Few-shot两条输入→输出示例，分别覆盖 overpackaged 与 salary_mismatch示例同时锚定"判什么"和"写到多细"，比形容词更有效
# Constraints只输出一条最严重信号；列出硬规则已覆盖的 6 类并禁止重复；禁止臆测；reason 引用原文；confidence 范围负向边界 + 输出质量要求，是第 15 页展开的核心

节选：分类法与约束（真实 Prompt）

# Task
阅读用户提供的招聘 JD 全文，识别规则引擎无法覆盖的语义陷阱，仅限以下四类：
1. pua_culture：狼性文化、PUA 式管理话术，如“公司是家”“不加班就是不奋斗”…
2. overpackaged：过度包装、画大饼，只描述福利、期权、发展空间，却不提业务与薪酬。
3. broad_duty：职责极度宽泛、一人干全栈，且无清晰边界。
4. salary_mismatch：要求极高（全栈、总监级、多领域精通）但薪资远低于市场合理区间。

# Constraints
1. 只输出一条最严重、最典型的语义信号，且判定依据必须能在 JD 原文中找到对应表述。
2. 不要提取硬规则已经覆盖的内容，出现下列情况一律忽略：
   - 薪资“面议”或薪资范围上下限差距超过 2 倍（salary_opacity）
   - “完成相关工作”“协助部门事务”等职责套话（vague_duty）
   - 同时要求“资深/专家”与“应届/小白/无经验”（contradictory_req）
   - “急招/火速/urgent”但未写明具体业务线（urgency_noise）
   - “培训费/押金/先培训后上岗/包就业”（scam_risk）
   - “抗压/能吃苦”与“单休/大小周”同时出现（overwork_risk）
   注意：硬规则只判断薪资是否透明，不判断薪资与要求是否匹配；
   要求极高但薪资极低，仍应提取 salary_mismatch。

三个容易被忽略的写法

用"仅限"而不是"包括"："仅限以下四类"是封闭集合，"包括以下四类"会被理解为开放式举例，模型可能输出第五类。

用"必须能在原文找到对应表述"：把"可解释"从后端要求前置到生成阶段，减少"听起来对但原文没写"的臆测。

用"注意"单独澄清边界："硬规则只管薪资是否透明，不管薪资与要求是否匹配"——如果不写这句，模型会因为看到 salary_opacity 出现在负向清单里，而连带放弃 salary_mismatch。

04 · NEGATIVE BOUNDARY

负向边界：告诉模型"别做什么"，比"要做什么"更有效

规则与模型是两套独立的判断系统，如果只正向描述"识别语义陷阱"，模型会自然地把"薪资面议"也当成语义陷阱再报一遍，导致同一风险出现两条记录、用户无法判断该信谁。

做法：把硬规则的判定条件翻译成"已处理清单"

硬规则Prompt 中的负向表述如果不写会怎样
salary_opacity薪资"面议"或上下限差距超过 2 倍 → 忽略模型重复报"薪资不透明"
vague_duty"完成相关工作""协助部门事务"等套话 → 忽略模型把职责套话当 broad_duty
contradictory_req"资深/专家"与"应届/小白"同时出现 → 忽略模型误判为岗位定位混乱
urgency_noise"急招/火速/urgent"但无业务线 → 忽略模型把紧迫话术当 PUA
scam_risk"培训费/押金/包就业" → 忽略模型重复报招转培
overwork_risk"抗压"与"单休/大小周"同时出现 → 忽略模型把加班文化重复报成 PUA

关键细节：只划"判定条件"，不泄露"实现方式"

Prompt 里写的是规则什么时候触发，不是正则长什么样。这样既能让模型避开重复，又不会让它试图"模仿规则"——模仿会导致模型输出规则本该输出的确定结论，反而污染来源标记。

一条容易被写错的边界

Prompt 原文 注意：硬规则只判断薪资是否透明（面议 / 跨度异常），不判断薪资与要求是否匹配；要求极高但薪资极低，仍应提取 salary_mismatch。

这是一条"负向清单的例外"。如果只写"薪资相关归规则管"，模型会把"要求精通四个方向、薪资 4–6K"也放过——但规则只看数字跨度，看不出"要求与回报不匹配"。这句话把两个相邻但不同的判断切开，是 V2 迭代中真正提升召回的一处修改。

为什么负向约束比正向清单更稳

正向清单定义的是"要抓什么"，边界是开放的，模型会不断外推；负向清单定义的是"不要碰什么"，边界是封闭的，且与规则引擎的覆盖范围一一对应。两者配合后，规则的归规则、语义的归语义，合并时冲突就只剩极少数情况。

即便这样，仍可能出现同类型冲突。此时由编排层兜底：同 signalType 保留 RULE 来源（详见 P11）。Prompt 负向约束降低冲突概率，代码裁决保证冲突结果唯一。

        return ExtractedSignal.ok(parsed.signalType(), parsed.reason(), confidence, raw);
    } catch (Exception e) {
        log.warn("LLM 输出解析失败，转入 pending_review，原始响应={}", raw, e);
        return ExtractedSignal.pendingReview(raw);   // 不抛异常，不阻断主流程
    }
}

原始响应只写日志、不落库、不回显给用户；日志级别为 WARN，便于线上定位模型输出漂移。

三类生成内容的闸门

对象机械检查失败时的行为
aiVerdict去掉引号与换行 → 空串转 null → 超过 30 字截断返回 null，前端隐藏整块，不显示空卡片
avoidanceTips逐行剥离序号 / 引号 / 句末标点 → 丢弃以"？"或"?"结尾的行 → 每条截断 30 字 → 最多 3 条返回空列表；无风险信号时直接跳过模型调用
questions逐行剥离序号 → 按 (?<=[？?]) 零宽切分 → 只保留问句 → 句末统一为"？" → 最多 3 条模型异常时由全局异常处理返回友好错误；无问号整行兜底补问号

两个具体例子

模型把锦囊写成问句怎么办？解析层有一行 .filter(line -> !line.endsWith("？") && !line.endsWith("?"))。这一行直接丢弃越界内容，而不是"改写"或"保留待人工处理"——因为问句属于另一个字段的职责，混进来就是错的。

模型把两个问句写在一行怎么办？按问号零宽切分，保留问号本身，一行变两条；混在后面的陈述句（如"请告知"）因为不以问号结尾被剔除。整行没有问号时兜底补一个"？"，避免过度过滤导致空结果。

闸门的优先级

1. 不阻断主流程
语义提取、锐评、锦囊的失败都不影响规则结果与落库；只有反问接口本身失败才返回错误。
2. 不伪装成功
提取失败写入 AI_SERVICE_DOWN 系统信号；锐评失败返回 null；锦囊失败返回空列表。
3. 不污染缓存
降级结果不写 Caffeine；AI 恢复后同一段 JD 会重新走语义提取，而不是 24 小时内一直拿到坏结果。
为什么不用 json_schema 强约束？当前端点（deepseek-chat）不支持 OpenAI 的 json_schema 响应格式，实测返回 "This response_format type is unavailable now"，因此降级为 json_object。字段与类型约束由 Prompt 的输出契约 + 服务端的显式校验共同保证——这也是为什么不把"格式正确"完全押在模型能力上。

为什么注入的危害被限制在"误导分类"，而不是"越权执行"

系统从不执行模型返回的任何指令：模型输出只被当作字符串解析成 ExtractedSignal，然后映射为数据库记录。即使模型被诱导说"删除数据"或"调用某接口"，这些文本也只会变成一条 signalType 奇怪的记录，不会触发任何动作。真正的危害是误导分类——把有风险的 JD 判成 none，让用户误以为安全。

对这一危害的缓解不是"更强的 Prompt"，而是规则兜底 + 来源可见：规则结果独立于模型存在，用户能看到每条信号来自 RULE 还是 LLM，也能看到 AI 是否降级。

从错误到约束的三步法

第一步：可复现
先写一个能稳定触发错误的场景（测试、curl、浏览器操作），确保不是偶发。
第二步：改结构
优先改架构或契约，而不是在出错处打补丁。能拆 Bean 就不加 try-catch。
第三步：固化
把场景写成测试，或写进项目规约。没有固化的修复，下一次生成还会犯。

两个最值得说的教训

"能跑"不等于"正确"。案例 3 中，代码没有抛异常、接口返回 200、日志一切正常——但降级逻辑已经失效。这类"静默错误"只能靠针对性的测试发现，靠人工点页面永远看不出来。

版本兼容性不能靠 AI 的记忆。案例 1 的根因是两个库的传递依赖冲突，AI 生成的依赖配置在语法上完全正确。解决它靠的是实际启动、看堆栈、查依赖树，而不是再问一次模型。

为什么不做"看起来更 AI"的方案

06 · REPRODUCIBILITY

可复现性：分三层说，才说得清楚

"可复现"常被混着用。这里拆成三层：环境能否一样、行为能否一样、结论能否一样。前两层可以做到严格一致，第三层只能做到流程与结构一致——任何依赖大模型语义判断的系统都无法承诺逐字复现。

① 环境可复现
同一套锁定版本、同一份 schema、零外部服务依赖。评委的机器与开发机在依赖层面等价。
② 行为可复现
规则判定、接口契约、降级路径、事务回滚都是确定的；相同输入必得相同结构与相同规则信号。
③ 结论可复现
判定流程、来源标记、边界处理可复现；模型措辞与语义召回不承诺逐字一致，用缓存与测试收窄波动。

结语

这个作品真正想证明的不是"AI 能写出一份求职建议"，而是：当 AI 的输出会被用户当作决策依据时，工程的重心必须从"让它说得更好"转向"让它错得更可控"。

规则负责确定性，模型负责语义；Prompt 负责倾向，代码负责边界；测试负责验收，降级负责兜底。四组关系共同构成了这个系统的可复现性与可信度——也是这份文档想留下的、比功能列表更重要的东西。
